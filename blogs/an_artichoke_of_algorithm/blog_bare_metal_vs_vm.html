Bare Metal vs. Virtual Machines: Why Building Bare Metal Is So Much Fun

Arghya Bhattacharya · March 2026 · 9 min read
A quick disclaimer I work on bare metal cloud infrastructure at Google. Views here are my own, and everything in this post sticks to public, industry-wide bare metal concepts rather than the internal design of any specific cloud provider.
TL;DR A bare metal instance hands the customer an entire physical server with no hypervisor in between. To make that feel like a cloud instance—with elastic networking, cloud disks, and API-driven power control—every piece of provider software has to move off the main host CPUs and onto separate management and offload processors inside the box. That single constraint changes how you monitor, maintain, scrub, and update a server, and that is what makes it so much fun to build.

A mental model: renting an apartment vs. renting the house

A virtual machine (VM) is like an apartment in a managed building. The landlord (the cloud provider) owns the building, keeps a master key, runs the plumbing, and can even move you to an identical apartment overnight while you sleep, without you noticing. That overnight move is live migration.

A bare metal instance is like renting the entire house. You get every room and you can remodel the kitchen (run your own OS kernel, or bring your own hypervisor). The landlord does not get a key. Yet the landlord still has to deliver water, electricity, and internet, read the meters, and notice if a pipe bursts. All of that has to happen from the outside: from the utility box at the curb.

Bare metal engineering is the art of building a really good utility box.

Anatomy of a modern cloud server

Traditional dedicated-server hosting (and open-source frameworks like OpenStack Ironic) provisions bare metal using a motherboard management controller plus top-of-rack switch and PXE-boot automation. Modern hyperscaler clouds go a step further: they pair the server with a dedicated hardware offload card—known across the industry as a DPU, IPU, or SmartNIC (public examples include AWS Nitro, Azure Boost, NVIDIA BlueField, Intel IPUs, and Google Cloud Titanium).

Viewed that way, a modern cloud server is not one computer—it is a small team of independent computers sharing one chassis:

  • Host Server (Main CPUs & Memory): the big x86 or Arm sockets and DRAM where customer workloads run.
  • Offload Card (DPU / IPU / SmartNIC): a separate computer on the PCIe bus—with its own general-purpose cores, hardware crypto/storage/packet engines, and an onboard root-of-trust controller that boots and secures the card itself.
  • BMC & Hardware Root of Trust: an always-on Baseboard Management Controller on the motherboard (often paired with a dedicated security microcontroller) that controls power, reads physical sensors, logs hardware faults, and verifies firmware integrity.

Both a virtualized host and an offloaded bare metal host can share this exact hardware layout. What changes is who runs what, where. Flip the switch below and watch the provider software vacate the host server:

On a standard VM host, the provider owns the host OS and hypervisor. Provider daemons run right on the main CPUs: they spawn VMs, enforce isolation, read hardware counters in-band, and coordinate maintenance. Even when an offload card accelerates packet and storage processing, the host CPU is still trusted territory.

On a bare metal host, the customer owns the host OS from the moment UEFI hands off control. From the provider's point of view, the host server is completely untrusted: zero provider agents run on the host CPUs, and the host has no path to the provider's internal management network. Every capability that makes a cloud instance feel "cloud-native" has to live outside the host:

  • Instance lifecycle (boot, stop, reboot, serial console, teardown) runs externally via the offload card and BMC.
  • Software-defined networking runs on the offload card. The host OS sees a standard PCIe network device while VPC routing, firewall rules, and line-rate encryption happen on the card.
  • Cloud block storage is emulated in hardware on the card as standard PCIe NVMe drives—so an unmodified customer OS can attach (and boot straight from) remote cloud disks with zero storage agents installed.
  • Zero host CPU tax: 100% of the host cores, caches, performance counters, and hardware extensions stay available to the tenant.

I call this the offload imperative: the goal is to make a bare metal instance look and feel like a whole-machine cloud VM—complete with elastic VPC networking and cloud block storage—while having none of the usual footholds on the host.

Difference #1: Telemetry has to come through the side door

On a VM host, if a memory DIMM starts throwing correctable ECC errors or a CPU core throttles, a daemon inside the host kernel sees it immediately. On bare metal there is no host daemon. Out-of-band (OOB) management via the BMC becomes the primary window into hardware health: ECC syndromes, temperatures, voltages, fan speeds, power rails, UEFI POST codes, hardware boot-watchdog timers, and firmware versions.

Cloud health services poll or stream telemetry from the BMC—commonly over the industry-standard DMTF Redfish API on an isolated management plane—to diagnose failing parts and trigger repairs. Inject a fault below, then cut the management link:

Two engineering problems immediately pop out. First, if the BMC hangs or the OOB link drops, you go blind—you cannot tell whether the server crashed or just your sensor path broke—so the telemetry pipeline itself needs health checks and recovery. Second, standard server boards normally expose in-band host-to-BMC channels such as legacy IPMI (/dev/ipmi0) or the DMTF Redfish Host Interface (a virtual USB/PCIe network socket to the BMC). On public cloud bare metal, giving an untrusted root user raw BMC access is out of the question—a tenant could flash firmware, alter UEFI settings, or wedge the management processor—so raw in-band channels are disabled or blocked in hardware. Whenever tenants or guest tools legitimately need hardware health, serial console output, or power actions, clouds mediate them through a strictly scoped API or allowlisted Redfish proxy that strips BMC credentials and permits only safe verbs. Reasoning about exactly which operations can safely cross that proxy boundary is a classic bare metal security design problem.

Difference #2: No live migration safety net

For VMs, live migration is magic. When a physical server needs a motherboard repair or a host-kernel patch, the hypervisor copies VM memory pages over the network to a healthy server with a sub-second pause, and the tenant barely notices. On bare metal, there is no hypervisor underneath to move you: your OS is bound directly to that physical silicon, its PCIe topology, and its local memory.

That means any maintenance that resets the host, replaces hardware, or reboots an offload card carrying active VPC and storage I/O is disruptive to that instance. Instead of an invisible background move, bare metal clouds coordinate planned maintenance windows with the customer (or rely on the customer's own cluster layer—like Kubernetes, VMware HA, or database replication—to drain workloads first).

Without live migration as a safety net, shrinking customer disruption becomes an architectural priority. Teams invest heavily in turning disruptive updates into non-disruptive (hitless) updates wherever hardware allows—such as live-patching Linux kernels on management/offload processors, or restarting DPU control-plane daemons in place while hardware flow tables and NVMe queues keep forwarding packets and I/O uninterrupted. And when a cold reboot truly is required, updates across BIOS, BMC, and offload cards have to be batched into unified maintenance bundles, paired with early OOB fault prediction, so customers experience one planned window rather than death by a thousand reboots.

Difference #3: One physical fleet, two personalities—and what a "reinstall" really means

Because virtualization, VPC networking, and block storage live on external offload cards rather than on the motherboard, modern clouds do not have to buy separate servers for VMs and bare metal. They can run a fungible fleet where the exact same physical server has two personalities: in virtualized host mode, the host boots the provider's verified OS and hypervisor to slice the box into multi-tenant VMs; in bare metal mode, no provider OS runs on the host at all, and a single customer boots their own OS straight from an offloaded NVMe volume.

Managing transitions across—and within—those two modes is governed entirely by trust boundaries. Even staying inside bare metal mode, deleting an instance is nothing like milliseconds-long VM teardown: because Tenant A had raw Ring-0 and PCIe access, the server must go through a cold power cycle, local storage sanitization, and cryptographic firmware attestation before Tenant B can touch it.

Notice the asymmetry when a server switches personalities. Moving a virtualized host into the bare metal pool starts from a machine the provider already controls: drain VMs, scrub local flash, reconfigure the offload card and BMC to wall off internal networks, verify attestation, and mark it ready. Moving back from bare metal to the virtualized fleet is another story: an untrusted kernel owned every CPU register and local disk sector, so returning to trusted fleet duty mandates a full automated bare-metal reinstall (clean-slate re-provisioning).

At cloud scale, "reinstall" does not mean a technician with a USB stick—it is an unattended, out-of-band imaging pipeline: the BMC and offload card cold-cycle the host, cryptographically erase all local NVMe/boot media, reset UEFI/BIOS settings, and verify every firmware hash from a hardware root of trust; next, the host network-boots a minimal signed provisioning kernel (over an isolated boot VLAN or virtual media exposed by the offload card), streams a fresh, bit-for-bit verified provider host OS and hypervisor image onto the boot drive, and validates measured-boot PCRs before the machine is allowed anywhere near multi-tenant VMs again.

Difference #4: Multi-controller release bundles and raw PCIe devices

Updating a virtualized host mostly centers on one provider-controlled host OS. On an offloaded bare metal server, software and firmware span several independent subsystems—system BIOS/UEFI, BMC, hardware root-of-trust microcontrollers, and the offload card—each with its own boot sequence and rollback rules. Across a fleet of different CPU generations, NICs, and accelerator trays, release composition itself becomes a design problem: deciding what belongs in a locked-step platform firmware bundle, what needs a hardware-SKU-specific override, and what can ship as an independently live-updatable control-plane package without breaking UEFI Secure Boot or Measured Boot chains.

The guest device model is rawer too. Instead of paravirtual interfaces (virtio and friends) where a hypervisor smooths over hardware quirks behind a synthetic device, a bare metal tenant interacts directly with PCIe physical functions—high-speed NICs, NVMe controllers, GPUs, or RDMA fabrics. Making sure standard OS drivers, IOMMU mappings, and PCIe function-level resets behave cleanly across whatever OS or third-party hypervisor a customer brings makes every new hardware generation genuinely interesting.

So why is it fun?

Hover over (or tap) a card to flip it.

🧅

You touch every layer

UEFI/BIOS, BMCs, DPUs/SmartNICs, Linux kernels, fleet automation, and cloud APIs. A single investigation can take you from a voltage sensor all the way up to the cloud console.
🕸️

A distributed system in one box

Multiple independent computers inside one chassis—host CPUs, offload card, BMC, and security controllers—have to agree on machine state. Timeouts and race conditions happen inside a single server.
🔐

Security is the design

The tenant has Ring-0 access to the physical host, so every boundary—PCIe buses, scoped BMC proxies, storage scrubbing, power cycles, and attestation—is a first-class design problem.
🕵️

Debugging is detective work

You cannot SSH into the host OS. You reconstruct what happened from BMC event logs, Redfish sensors, POST codes, and offload-card telemetry. Solving those mysteries is deeply satisfying.
🎪

No safety net

Without live migration, every maintenance workflow, firmware rollout, and hardware repair is felt by real workloads. It pushes you to engineer carefully and measure everything.
🚀

New silicon in the raw

New CPU generations, PCIe speeds, and accelerators keep arriving, and bare metal is where customers meet new hardware in its purest, un-virtualized form.
🤝

Cross-stack collaboration

Virtual networking, cloud block storage, RDMA, accelerators, firmware, and hardware security all converge on the physical box—so you constantly learn from experts across the stack.
🎯

Workloads that truly need it

Customers running third-party hypervisors, large in-memory databases, strict per-socket licenses, or ultra-low-jitter workloads cannot use ordinary VMs. You build the foundation they rely on.

Wrapping up

Engineering bare metal in the cloud is a fun inversion of traditional systems design: you hand the main computer to the customer, move the cloud's control and data planes onto surrounding silicon, and lean on out-of-band telemetry and hardware-rooted security to keep the fleet healthy and trustworthy. Every constraint turns routine VM assumptions into fresh systems puzzles—and solving those puzzles is why I love working in this space.

A big thank you to my teammates working on Bare Metal at Google, past and present, for always making time for questions, sharing deep systems knowledge in tech talks and hackathons, and making day-to-day engineering so collaborative.
